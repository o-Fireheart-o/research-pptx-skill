# 연구 제안서·연구 보고서 PPT 작성

사용자는 연구자다. 정해진 양식(기관 지정 양식, 연구실 템플릿, 지난 문서)이 있고, 그 양식에 맞는 제안서나
보고서를 만들려고 한다. 이 스킬의 일은 세 가지다. **양식의 규칙을 읽어 내고, 무엇을 어떤 논리로 말할지
먼저 합의하고, 합의한 내용을 양식대로 문서로 만든다.**

연구 문서는 읽는 사람이 평가자다. 제안서는 "이 연구를 왜, 이 사람들이, 이 방법으로 해야 하는가"를
설득하고, 보고서는 "약속한 것을 했고 무엇을 알아냈는가"를 증명한다. 그래서 슬라이드의 모양보다 **논리의
이음새**(문제 → 목표 → 방법 → 결과가 서로 대응하는가)와 **근거의 정확성**이 결과물의 품질을 정한다.

## 가장 중요한 원칙: 근거 없는 내용을 만들지 않는다

연구 문서에서 그럴듯하게 지어낸 숫자나 문헌은 문서 전체의 신뢰를 무너뜨리고, 연구 윤리 문제가 된다.

- 데이터, 수치, 통계값, 실험 결과는 사용자가 준 자료에 있는 것만 쓴다. 비어 있는 값을 추정으로 채우지
  않는다.
- 참고문헌은 사용자가 준 것, 또는 직접 찾아 실제로 있음을 확인한 것만 쓴다. 기억에 의존해 저자·연도·
  학술지를 적지 않는다.
- 근거가 없어 채울 수 없는 자리에는 `[확인 필요: 무엇이 필요한지]`, 출처를 모르는 주장에는
  `[출처 필요]`를 남기고, 보고할 때 목록으로 알린다. 빈칸을 숨기는 것보다 보이는 편이 사용자에게 낫다.
- 결과의 해석을 자료보다 강하게 쓰지 않는다("경향이 보임"을 "입증함"으로 바꾸지 않는다). 표현을
  다듬다가 주장의 세기가 바뀌면 사용자에게 알린다.
- 그래프는 사용자가 준 원 데이터나 그림으로 만든다. 보기 좋게 하려고 값을 고치거나 축을 바꾸지 않는다.

## 사용자와 일하는 방식

사용자는 개발자가 아닐 수 있다. 스크립트 이름, 파일 형식 같은 내부 사정은 말하지 않고 **무엇을 정해
달라는지**만 쉬운 말로 묻는다. 질문은 한 번에 서너 개까지, 가능하면 선택지와 권하는 쪽을 함께 낸다.
연구 내용의 판단(무엇이 핵심 기여인지, 어떤 결과를 앞세울지)은 사용자의 몫이다. 구성과 표현을 제안하되
연구 내용을 대신 정하지 않는다.

## 전체 흐름

| 단계 | 하는 일 | 산출물 | 사용자 확인 |
|---|---|---|---|
| 0. 입력 확인 | 문서 종류, 양식, 평가 기준, 연구 자료, 분량·시간 | 작업 폴더 | 빠진 것만 질문 |
| 1. 템플릿 분석 | 슬라이드 유형, 서식, 정해진 목차 읽기 | `work/template_profile.md` | 요약 보고 |
| 2. 스토리라인 제안 | 핵심 주장과 논리 흐름을 뼈대 덱으로 제안 | `storyboard.pptx`, `storyline.md` | **확정받고 다음 단계로** |
| 3. 자료 준비 | 그림, 그래프, 표, 일정, 참고문헌 정리 | `figures/`, 자료 목록 | 부족한 자료 요청 |
| 4. 샘플 슬라이드 | 대표 한두 장을 양식대로 먼저 제작 | `output/sample.pptx` | **승인받고 다음 단계로** |
| 5. 전체 조립 | 승인된 샘플의 방식으로 전체 제작 | `output/<파일명>.pptx` | — |
| 6. 검수 | 렌더링 확인, 논리·근거·번호 점검 | 확인 요청 목록 | 결과 보고 |
| 7. 수정 반복 | 피드백과 사용자 직접 수정 반영 | 갱신된 덱, 백업 | — |
| 8. 파생판 | 발표용 축약본, 영문판, 다음 보고서 | 별도 파일 | 필요할 때만 |

확인받는 지점은 두 곳이다. **스토리라인**(무엇을 어떤 순서로 말할지)과 **샘플 슬라이드**(한 장이 어떤
모습과 밀도로 나올지). 구성이 바뀌면 그림 번호·목차·대응표가 함께 움직이고, 배치나 글 밀도가 바뀌면
모든 장을 다시 만들어야 한다. 둘 다 앞에서 확인하는 편이 다 만든 뒤 고치는 것보다 훨씬 빠르고 싸다.
사용자가 "일단 만들어 봐"라고 하면 확인 단계를 줄이되, 건너뛴 사실과 그 때문에 다시 만들 수 있다는
점을 한 줄로 알린다.

## 0. 입력 확인

대화나 받은 파일에서 알 수 있는 것은 묻지 않는다.

- **문서 종류**: 제안서인가 보고서인가. 보고서면 중간(연차)인가 최종인가.
- **쓰이는 상황**: 발표 평가용(발표 시간, 질의응답 유무)인가, 제출해서 읽히는 문서인가, 둘 다인가.
  분량과 글의 밀도가 여기서 정해진다.
- **양식**: 템플릿 파일이나 지난 문서. 기관이 목차나 분량을 정해 두었는지(공고문, 작성 요령).
- **평가 기준**: 공고문(RFP)의 평가 항목과 배점, 심사위원의 성격(같은 분야 전문가인가, 인접 분야인가).
  제안서에서는 이것이 구성의 기준이다.
- **연구 자료**: 연구 내용의 출처. 초안 문서, 논문, 실험 결과, 데이터, 그림, 지난 제안서(보고서의 경우
  약속했던 목표가 여기에 있다).
- **언어, 파일명, 마감**.

작업 폴더가 아직 없으면 직접 만든다. 사용자에게 폴더를 만들라고 시키지 않는다.
`python -I <skill>/scripts/init_project.py "<폴더>"`가 아래 구성과 안내 파일(`시작하기.md`, `AGENTS.md`,
`work/NOTES.md`)을 만들고, 지금 무엇이 비어 있는지와 다음에 할 일을 알려 준다(없는 것만 만들고 기존 파일은
건드리지 않는다). 폴더 준비만 요청받았을 때의 안내 방식은 `research-pptx-init` 스킬에 있다. 양식이나 자료가
비어 있으면 어느 폴더에 무엇을 넣을지 알려 주고 기다린다.

작업 폴더는 아래 구성을 쓴다. 이미 다른 구성이 있으면 그쪽을 따른다.

```
storyboard.pptx  뼈대 덱 (사용자가 PowerPoint에서 보고 고치는 스토리라인)
storyline.md   같은 내용의 글 파일 (만드는 쪽이 관리. 사용자가 직접 고쳐도 된다)
template/      양식 원본 (고치지 않는다)
source/        연구 자료 (공고문, 초안, 논문, 데이터, 지난 문서)
figures/       슬라이드에 넣을 그림·그래프
work/          템플릿 프로필, 대응표, 작업 기록, 빌드 스크립트 (만드는 쪽이 관리)
output/        완성 pptx,  output/backup/  단계별 백업
```

## 1. 템플릿 분석

먼저 **양식 보관함**(`~/.research-pptx/profiles/`)에 같은 양식의 프로필이 있는지 본다. 있으면 그것을
`work/template_profile.md`로 가져와 양식 파일이 그때와 같은지만 확인하고 분석을 건너뛴다. 없으면 양식을
눈으로 보고 구조를 읽은 뒤 **템플릿 프로필**을 쓴다. 이후 모든 슬라이드는 이 프로필에 맞춘다. 방법,
양식, 보관함 쓰는 법은 `references/template-profile.md`에 있다.

연구 문서에서 특히 볼 것:
- 기관이 **정해 둔 목차**가 있는가(있으면 순서와 제목을 바꾸지 않는다).
- 그림·표 캡션, 출처 표기, 쪽 번호의 위치와 표기법.
- 표, 그래프, 일정표, 체계도의 본보기가 있는가.
- 지난 문서가 샘플이면 구성과 문체도 본보기다(개조식인가 서술식인가, 제목이 주제형인가 주장형인가).

프로필에 없는 디자인 요소(새 색, 새 글꼴, 장식)는 만들지 않는다. 양식에 본보기가 없는 유형이 필요하면
가장 가까운 유형을 변형하고 그 사실을 알린다.

## 2. 스토리라인 제안

스토리라인은 사용자에게 **뼈대 덱**(`storyboard.pptx`)으로 보여 준다. 1번 장은 전체를 한 장에 담은
흐름도이고, 그 뒤로 실제 슬라이드 한 장마다 기획 장이 하나씩 있다(제목 = 그 장의 결론, 본문 = 담을 내용,
점선 상자 = 넣을 그림, 빨간 `?` = 못 정한 것). 사용자는 PowerPoint에서 슬라이드를 끌어 순서를 바꾸고
글을 고친다. 사람은 슬라이드로 된 흐름을 가장 빨리 이해하기 때문이다. 만드는 쪽은 같은 내용을 글 파일
`storyline.md`로 관리하고, 뼈대 덱을 읽을 때마다 갱신한다. 만들고 읽는 법과 주고받는 순서는
`references/storyline-format.md`, 제안서·보고서별 흐름과 논리 점검은 `references/storyline.md`에 있다.

1. 사용자가 가진 것에서 시작한다. 자료만 있으면 초안을 써 주고, 제목 몇 개나 말로 흐름을 받았으면
   내용을 채우고, 이미 만든 개요나 PPT가 있으면 그대로 옮긴다.
2. **핵심 주장 한 문장**을 먼저 맞춘다. 제안서는 "<문제>를 <접근>으로 풀어 <성과>를 낸다", 보고서는
   "<목표>에 대해 <결과>를 얻었고 이는 <의미>다".
3. 구성은 양식이 정한 목차, 평가 항목, 문서 종류별 흐름(국가 연구개발 과제 발표는 대개 필요성 → 목표·
   내용 → 추진 전략 → 수행 역량 → 활용·기대 효과) 순으로 따른다.
4. **논리 사슬**을 맞춘다. 제안서는 문제 → 목표 → 내용 → 성과, 보고서는 목표 → 수행 → 결과 → 달성도.
   평가 기준이 있으면 평가 항목 대응표도 만든다(`work/logic_check.md`).
5. `python -I <skill>/scripts/storyline_check.py storyline.md`로 장별 분량, 발표 시간 대비 장수, 비어
   있는 장, 없는 자료, `?` 목록을 확인한 뒤 `storyboard.py make`로 뼈대 덱을 만들어 준다. 흐름도부터
   보고 제목만 이어 읽어 보라고 안내하고, 정할 것 서너 개를 묻는다.
6. 사용자가 뼈대 덱을 고쳤으면 `storyboard.py read`로 읽어 `storyline.md`를 갱신하고 흐름도를 다시
   그린다(`storyboard.py map`). 말로 받은 수정은 두 파일에 함께 반영한다. 바뀐 점을 되짚어 확인받고,
   확정되면 작업 기록에 남긴다.

자료에 없는 내용은 지어내지 않고 `?`로 남긴다. 사용자가 쓴 결론 문장의 뜻과 세기를 바꾸지 않는다.

## 3. 자료 준비

`references/figures.md`에 그림·그래프·표·도식·참고문헌 다루는 법이 있다.

- 목차에 적은 필요 자료를 목록으로 만들고, 있는 것과 없는 것을 나눈다. 없는 것은 한 번에 요청한다.
- 그래프는 가능하면 데이터로 다시 그려 편집 가능한 차트로 넣는다. 그림 파일만 있으면 그대로 쓰되
  해상도를 확인한다.
- 추진 일정, 연구 체계도, 개념도는 템플릿 도형 서식으로 그린다(수정과 번역이 가능하도록).
- 다른 문헌의 그림을 쓰면 출처를 표기하고, 재사용 허락이 필요한지는 사용자에게 알린다.
- 미공개 데이터, 개인 정보, 참여자 식별 정보가 보이면 넣기 전에 확인한다.

## 4. 샘플 슬라이드

전체를 만들기 전에 **대표 슬라이드 한두 장**을 양식대로 완성해 보여 주고 승인받는다. 방법은
`references/build.md`의 "샘플 슬라이드"에 있다.

- 고르는 기준: 글과 표가 가장 많은 장 하나, 그림이나 도식이 중심인 장 하나. 표지나 목차는 샘플로 삼지
  않는다(양식이 정해 줘서 확인할 것이 없다).
- 렌더링한 그림과 파일(`output/sample.pptx`)을 함께 주고 묻는다. 글의 양, 글자 크기, 그림과 글의 배치,
  결론 줄의 위치, 양식의 장식과 어울리는지.
- 승인되면 그때 정해진 것(글 밀도, 글자 크기, 배치 방식, 표 서식)을 `work/NOTES.md`에 적고, 나머지 장은
  **같은 방식으로** 만든다. 장마다 방식을 바꾸지 않는다.
- 건너뛰어도 되는 경우: 같은 양식으로 승인받은 기록이 보관함의 프로필에 있을 때, 사용자가 건너뛰자고
  할 때, 다섯 장 이하의 짧은 덱일 때.

## 5. 전체 조립

`references/build.md`를 따른다.

- 템플릿을 `output/`에 복사해 편집한다. 원본은 고치지 않는다.
- 전체를 **한 번의 스크립트 실행**으로 만든다. 장마다 따로 맡기거나 서브에이전트를 붙이지 않는다
  (용어와 번호가 어긋나고 비용이 크다).
- 덱은 다시 실행할 수 있는 스크립트로 만든다. 문구 하나를 고칠 때도 내용 데이터를 고치고 다시 만든다.
- 슬라이드는 템플릿의 레이아웃과 본보기 슬라이드로 만들고, 위치·크기·글꼴은 프로필 값을 쓴다.
- 샘플의 문구와 그림이 남지 않게 한다.
- 글자가 넘치면 글자 크기를 템플릿보다 줄이지 말고 문구를 줄이거나 장을 나눈다.

## 6. 검수

만든 덱은 반드시 렌더링해서 눈으로 본다. 점검 항목은 `references/qa.md`에 있다. 최소한:

1. 전 슬라이드 렌더링 → 모아 보기(`contact_sheet.py`)로 먼저 훑고, 문제가 보이는 장만 크게 연다 →
   글자 넘침, 겹침, 남은 샘플 문구
2. `python -I <skill>/scripts/deck_check.py <deck>` → 남은 `[확인 필요]`, 그림·표 번호, 인용 번호와
   참고문헌의 대응, 글이 너무 많은 장
3. 논리 점검: `storyline.md`의 모든 장이 덱에 있는가, 평가 항목 대응표와 논리 사슬 표가 덱과 맞는가
4. 수치 점검: 같은 숫자가 요약·본문·표에서 일치하는가, 단위가 있는가

보고는 **결과 / 확인이 필요한 것 / 내가 임의로 정한 것** 세 묶음으로 한다. 확인하지 못한 것을 확인했다고
쓰지 않는다.

## 7. 수정 반복

사용자가 PowerPoint에서 덱을 직접 고치면 그때부터 그 파일이 원본이다.

- 처음의 빌드 스크립트를 다시 돌리지 않는다(사용자가 고친 내용이 지워진다). 해당 슬라이드만 고친다.
- 고치기 전에 `output/backup/<이름> - <무엇을 하기 전> (<날짜>).pptx`로 백업한다.
- 사용자가 다듬은 문장과 배치는 유지한다. 요청받은 곳만 고친다.
- 슬라이드를 추가·삭제·이동했으면 목차, 그림·표 번호, "앞 장에서 본 바와 같이" 같은 참조를 다시 맞춘다.
- 파일이 PowerPoint에 열려 있으면(같은 폴더의 `~$파일명`) 저장이 충돌한다. 닫아 달라고 하거나 다른
  이름으로 저장하고 어느 파일이 최신인지 알린다.
- 지도교수·공동연구자의 의견이 서로 다르면 임의로 절충하지 말고 사용자에게 어느 쪽을 따를지 묻는다.

## 8. 파생판

`references/variants.md`를 따른다. 제출본에서 발표용 축약본 만들기, 영문판, 제안서에서 다음 보고서
뼈대 만들기를 다룬다.

## 완료 기준

아래가 모두 맞을 때만 "완성했다"고 말한다. 하나라도 아니면 **어느 단계의 몇 번 장에서 무엇 때문에
멈췄는지**를 보고한다.

- 스토리라인과 샘플 슬라이드가 승인됐다(건너뛰었으면 그 사실이 기록돼 있다).
- `storyline.md`의 모든 장이 완성본에 있고, 완성본에만 있는 장이 없다.
- 전 슬라이드를 렌더링해서 봤고 `work/progress.json`에 `막힘`인 장이 없다.
- 양식이나 지난 문서의 문구·그림이 남아 있지 않다.
- 스토리라인에 적힌 그림·표가 해당 장에 들어 있다. 없는 것은 자리 표시와 함께 보고 목록에 있다.
- 남은 `[확인 필요]`, `[출처 필요]`, `자료필요`·`확인필요` 장이 보고의 "확인이 필요한 것"에 모두 적혀 있다.
- 작성 요령(분량, 글자 크기 하한, 파일 이름)을 지켰다.

**막히면 멈추고 알린다.** 품질을 낮춘 대체물을 말없이 만들지 않는다. 연구 문서에서는 조용한 대체가
가장 위험하다. 해서는 안 되는 대체의 예:

- 없는 수치·그래프를 그럴듯한 값으로 채우기
- 원 데이터 없이 그림에서 값을 눈으로 읽어 그래프를 다시 그리기
- 렌더링이 안 돼서 보지 않은 덱을 검수했다고 하기
- 양식의 레이아웃이 안 맞는다고 양식과 다른 디자인으로 만들기
- 글이 안 들어간다고 내용을 말없이 빼거나 글자를 작성 요령보다 작게 줄이기

이런 상황에서는 그 장을 `막힘` 또는 `자료필요`로 기록하고, 무엇이 있으면 풀리는지와 함께 선택지를
제시한다. 나머지 장은 계속 진행한다.

## 진행 상태

**파일에 기록한다.** 대화에서 "만들었다"고 말한 것은 기록이 아니다. 며칠에 걸친 작업을 이어받을 때
기준이 되는 것은 파일이다.

```
python -I <skill>/scripts/progress.py init storyline.md work/progress.json     스토리라인 확정 뒤 (구성이 바뀌면 다시)
python -I <skill>/scripts/progress.py stage work/progress.json 5              단계가 넘어갈 때
python -I <skill>/scripts/progress.py set work/progress.json 3,5-7 만듦       장의 상태가 바뀔 때
python -I <skill>/scripts/progress.py show work/progress.json                 지금 상태 보기
```

장의 상태는 `대기 → 만듦 → 검수함`이 기본이고, 걸리는 것이 있으면 `자료필요`, `확인필요`, `막힘`에
이유를 적는다. `검수함`은 그 장의 렌더링을 실제로 본 뒤에만 쓴다.

**사용자에게 보여 준다.** 단계가 넘어갈 때마다 `show`의 단계 목록(아홉 줄, 지금 단계에 ▶)과 한두 줄
요약을 보여 준다. 사용자는 지금 어디쯤이고 무엇이 남았는지 알 수 있다. 단계 안에서 일일이 보고하지는
않는다.

## 사용량을 아끼는 방법

사용자는 사용량 한도가 있는 요금제를 쓴다. 한 덱을 만드는 데 한도를 다 쓰면 정작 고칠 때 쓸 수 없다.
품질을 깎지 않고 아낄 수 있는 곳에서 아낀다.

- **서브에이전트를 쓰지 않는다.** 장마다 에이전트를 붙이는 방식은 같은 자료와 규칙을 장수만큼 다시
  읽는다. 조립은 스크립트 한 번, 검수는 직접 한다.
- **참고 문서는 그 단계에서 한 번만 읽는다.** 이 문서의 표에 적힌 단계가 됐을 때 해당 파일을 읽고,
  다시 읽지 않는다. 해당 없는 문서(영문판을 안 만드는데 `variants.md`)는 읽지 않는다.
- **긴 자료는 한 번 읽고 정리해 둔다.** 공고문, 논문, 지난 보고서를 읽으면 쓸 내용을 쪽 번호와 함께
  `work/source_notes.md`에 적고, 이후에는 그 정리를 본다. 같은 PDF를 여러 번 열지 않는다.
- **스크립트의 요약 출력을 쓴다.** 덱의 내용을 볼 때 XML이나 전체 문구를 펼치지 않고 `deck_profile.py`,
  `deck_check.py`, `storyline_check.py`, `progress.py show`의 표를 본다. `--text`는 교정할 때만 쓴다.
- **그림은 모아서 본다.** 렌더링 확인은 `contact_sheet.py`로 아홉 장씩 모은 그림을 먼저 보고, 이상한
  장만 한 장씩 연다. 30장 덱을 한 장씩 여는 것보다 훨씬 적게 든다.
- **고친 장만 다시 만들고 다시 본다.** `ppt_export.ps1 -Slides "7,12"`로 바뀐 장만 렌더링한다.
- **양식 분석을 되풀이하지 않는다.** 보관함의 프로필을 쓴다.
- **질문과 보고는 모아서 짧게.** 질문은 한 번에 서너 개, 보고는 세 묶음. 스토리라인 전체나 스크립트
  내용을 대화에 붙이지 않는다(사용자는 뼈대 덱과 완성본을 직접 본다).
- **단계가 끝나면 새 대화로 이어 가도 된다.** 긴 대화는 매 답변마다 앞의 내용을 다시 읽는다.
  `work/NOTES.md`와 `work/progress.json`이 있으면 새 대화에서 그 둘만 읽고 이어 갈 수 있다. 스토리라인
  확정 뒤, 샘플 승인 뒤가 끊기 좋은 지점이다. 사용자에게 이 방법을 알려 준다.

아끼면 안 되는 곳: 근거 대조, 렌더링 확인, 두 번의 승인 단계. 이것을 건너뛰어 생긴 재작업이 가장 비싸다.

## 작업 기록

마감까지 여러 번 나눠 작업하게 되므로, 다음 작업 때 같은 기준으로 이어 갈 수 있게 `work/NOTES.md`에
날짜와 함께 적는다. 작업 폴더에 `AGENTS.md`(또는 `CLAUDE.md`)가 있으면 거기에 `work/NOTES.md`를 먼저
읽으라는 한 줄을 넣어 다음 작업 때 자동으로 읽히게 한다. 적을 것은 "다음에 모르면 잘못할 내용"이다.

- 사용자가 정한 규칙과 용어(예: 과제명 표기, 약어, 주장형 제목 사용)
- 샘플 슬라이드에서 승인된 것(글 밀도, 글자 크기, 배치 방식, 표 서식)
- 어느 파일이 원본인지, 다시 돌리면 안 되는 스크립트
- 범위 변경과 그 이유, 누구의 의견인지
- 아직 받지 못한 자료

## 환경

- Windows + PowerPoint를 기본으로 한다. 렌더링은
  `powershell -ExecutionPolicy Bypass -File <skill>/scripts/ppt_export.ps1 <deck> <dir>`.
  PowerPoint가 없는 환경에서는 LibreOffice(`soffice --headless --convert-to pdf`)로 하되, 글꼴이 대체돼
  글자 폭이 다를 수 있으므로 글자 넘침 판정에 여유를 둔다.
- Python 스크립트는 `python -I`로 실행한다. 필요한 패키지: `python-pptx`, `lxml`, `Pillow`.
  없으면 `python -m pip install python-pptx lxml Pillow`로 설치한다(설치 전에 사용자에게 알린다).
- `<skill>`은 이 SKILL.md가 있는 폴더다.
