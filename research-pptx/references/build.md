# 조립과 수정

## 원칙

- **스크립트로 만든다.** 슬라이드 내용을 데이터(목록, JSON)로 두고 스크립트가 덱을 만든다. 문구 하나를
  고칠 때도 데이터를 고치고 다시 실행한다. 수십 장을 같은 규칙으로 유지할 수 있고, 다음 작업 때
  이어받을 수 있다.
- **다시 실행하면 같은 결과.** 빌드 스크립트는 템플릿 복사부터 시작해 전체를 새로 만든다.
- **템플릿 원본은 읽기만.** `output/`에 복사한 파일을 편집한다.
- **Python은 `python -I`로 실행**한다.
- 스크립트와 내용 데이터는 `work/`에 둔다. 사용자에게는 스크립트 이야기를 하지 않고 결과와 확인할
  것만 말한다.

## 샘플 슬라이드

전체를 만들기 전에 대표 한두 장을 완성해 승인받는다. 여기서 정해지는 것은 **한 장이 어떤 모습과 밀도로
나오는가**이고, 승인된 방식이 나머지 모든 장의 기준이 된다.

1. **고른다.** 글과 표가 가장 많은 장 하나(양식에 내용이 들어가는지 가장 먼저 드러난다)와, 그림이나
   도식이 중심인 장 하나. 다섯 부 구성이면 보통 필요성 장의 현황 슬라이드와 목표·내용 장의 그림
   슬라이드다. 자료가 아직 없는 장은 고르지 않는다.
2. **만든다.** 전체 조립에 쓸 것과 같은 빌드 함수로 만든다. 샘플만 손으로 따로 만들면 나머지 장을 같은
   모습으로 만들 수 없다. 결과는 `output/sample.pptx`.
3. **본다.** 렌더링해서 글자 넘침과 겹침을 직접 고친 뒤 사용자에게 준다. 문제가 있는 샘플을 그대로
   보여 주고 판단을 떠넘기지 않는다.
4. **묻는다.** 그림과 파일을 주고 아래를 확인한다. 선택지가 있으면 권하는 쪽을 말한다.
   - 한 장에 들어간 글의 양이 맞는가(더 줄일지, 더 넣을지)
   - 글자 크기, 줄 간격, 표의 모습
   - 그림과 글의 자리, 결론 줄의 위치와 표기
   - 양식의 장식(위쪽 진행 표시, 소제목 띠 등)을 쓰는 방식
5. **기록한다.** 승인된 내용을 `work/NOTES.md`에 숫자로 적는다(예: 본문 14pt, 한 장 400자 안팎, 결론
   줄은 아래쪽 `→` 굵게, 표 머리글 색). 고쳐 달라는 말이 있으면 샘플을 고쳐 다시 확인받는다.
   승인 뒤 `progress.py stage work/progress.json 5`.
6. **이어 간다.** 전체 조립은 샘플과 같은 함수, 같은 값으로 한다. 샘플로 만든 장은 다시 만들지 않고
   그대로 포함한다.

샘플에서 승인된 값은 양식 보관함의 프로필에도 적어 둔다(`template-profile.md`). 같은 양식으로 다음
문서를 만들 때 샘플 단계를 건너뛸 근거가 된다.

## 초기 빌드

조립은 **스크립트 한 번의 실행**으로 전체를 만든다. 실행 뒤 `progress.py set work/progress.json all 만듦`
(자료가 없어 자리 표시만 둔 장은 `자료필요`, 만들지 못한 장은 `막힘`과 이유).

`python-pptx`로 슬라이드 유형마다 "레이아웃으로 슬라이드 추가 → 자리 표시자 채우기 → 프로필 좌표에
그림·표·도형 추가"를 함수로 만든다.

- 레이아웃은 번호가 아니라 이름으로 찾는다(템플릿마다 순서가 다르다).
- `text_frame.text = "…"`는 서식을 지운다. 기존 문구를 바꿀 때는 `run.text`를 바꾼다.
- python-pptx에는 슬라이드 복제 기능이 없다. 본보기 슬라이드를 복제해야 하면 `scripts/copy_slides.py`.
- XML을 직접 만질 때는 `lxml`을 쓴다. `xml.etree`로 다시 쓰면 네임스페이스 접두어가 바뀌어 파일이
  깨진다.
- 글머리 기호는 레이아웃의 것을 쓰고 단계(level)로 들여쓴다. `□`, `•`를 글자로 넣지 않는다(템플릿이
  글자로 넣은 관례라면 그대로 따른다).

### 지난 문서에서 시작할 때
지난 문서의 슬라이드를 본보기로 복제하는 방식이 가장 정확하다. 순서는 "필요한 유형의 슬라이드 복제·
정렬 → 쓰지 않는 슬라이드 삭제 → 내용 채우기"다. 내용을 채운 뒤 복제하면 채운 내용까지 복제된다.
지난 문서의 문구·그림·숫자가 한 군데라도 남으면 치명적이므로 검수에서 반드시 확인한다.

### 내용 채우기에서 자주 틀리는 것
- 양식의 자리 수와 내용 수가 다를 때(세부 목표 4칸 양식에 3개) 남는 칸은 글자만 지우지 말고 도형
  묶음째 지우고 간격을 다시 맞춘다.
- 제목 끝에 마침표를 찍지 않는다. 같은 유형의 슬라이드는 제목 위치·크기가 모두 같아야 한다.
- 글자가 넘치면 글자 크기를 템플릿(또는 작성 요령의 하한)보다 줄이지 않는다. 문구를 줄이거나 장을
  나누고, 무엇을 뺄지는 사용자에게 선택지를 준다.
- 그림은 프로필의 그림 영역에 비율을 유지해 넣는다. 두 그림을 나란히 놓으면 높이를 맞춘다.
- 표는 PowerPoint 표로 넣는다(그림으로 넣으면 수정할 수 없다).
- 수식은 그림으로 넣을 수밖에 없는 경우가 많다. 원본 수식(LaTeX, 수식 편집기)을 `work/`에 남긴다.
- 단어나 숫자와 단위가 줄 끝에서 갈라지지 않게 한다("30" / "%").

## 텍스트 상자와 글자 넘침

상자에 글이 들어가는지를 글자 수 계산으로 판단하지 않는다(한글·영문 폭, 글꼴 대체 때문에 실제와
어긋난다). 렌더링해서 눈으로 확인한다. 자리 표시자는 템플릿의 자동 맞춤 설정을 그대로 두고, 새로 만드는
텍스트 상자는 넉넉한 폭으로 잡는다.

## 사용자가 직접 고친 뒤

사용자(또는 지도교수, 공동연구자)가 PowerPoint에서 덱을 고치면 그 파일이 원본이다. 이때부터:

1. **빌드 스크립트를 다시 돌리지 않는다.** 고친 내용이 지워진다. `work/NOTES.md`에 "이 파일은 직접
   수정본, 빌드 스크립트로 다시 만들지 않음"을 날짜와 함께 적는다.
2. **고치기 전에 백업.** `output/backup/<이름> - <무엇을 하기 전> (<YYYY-MM-DD>).pptx`
3. **요청받은 곳만 고친다.** 바꿀 슬라이드와 도형을 특정해 그것만 바꾼다. 사용자가 다듬은 문장과 손으로
   옮긴 배치를 "더 좋게" 고치지 않는다. 고치고 싶은 곳이 보이면 제안으로 말한다.
4. **무엇이 바뀌었는지 먼저 본다.** 고친 파일을 받으면 `deck_profile.py`와 `deck_check.py --text`로
   이전 판과 비교해 구성이 어떻게 달라졌는지 파악하고, `storyline.md`를 덱에 맞춘다.
5. **슬라이드 번호가 바뀌면** 번호로 짠 스크립트는 맞지 않는다. 다시 쓰기 전에 현재 번호를 확인한다.
   특정 시점에 맞춘 스크립트는 머리말에 "1회 실행, <날짜>"라고 적는다.
6. **구조가 바뀐 뒤 다시 맞출 것**: 목차 슬라이드, 장 구분, 그림·표 번호, 본문의 참조("그림 3",
   "앞 장"), 인용 번호, 쪽 번호.
7. **열린 파일 확인.** 같은 폴더에 `~$<파일명>`이 있으면 PowerPoint에 열려 있는 것이다. 닫아 달라고
   하거나, 다른 이름으로 저장하고 어느 파일이 최신인지 분명히 알린다.

## 여러 사람의 의견 반영

- 의견을 받으면 목록으로 정리해 하나씩 처리하고, 처리 결과(반영 / 다르게 반영 / 반영 안 함과 이유)를
  표로 돌려준다.
- 의견끼리 부딪치면 절충안을 지어내지 말고 사용자에게 어느 쪽을 따를지 묻는다.
- 연구 내용을 바꾸는 의견(목표 수정, 결과 해석 변경)은 논리 사슬 표를 먼저 고친 뒤 슬라이드를 고친다.
  한 장만 고치면 다른 장과 어긋난다.

## 파일 이름

- 산출물: 사용자가 정한 이름(기관이 정한 파일명 규칙이 있으면 그것). 버전은 날짜로 구분한다.
- 작업 파일: `storyline.md`, `work/template_profile.md`, `work/build.py`, `work/NOTES.md`
- 그림: `figures/<슬라이드 주제>_<내용>.png` (슬라이드 번호는 바뀌므로 파일명에 쓰지 않는다)
